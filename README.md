# QueryGuard

QueryGuard — рабочее веб-приложение для выявления ресурсоёмких SQL-запросов в PostgreSQL торговой сети. Оно собирает фактическую статистику `pg_stat_statements`, рассчитывает интегральную токсичность вычислений, показывает динамику, оценивает энергопотребление и стоимость, а также поддерживает аудит, политики хранения и резервное копирование.

Проект реализует первую, программную часть курсовой работы по теме «Система выявления ресурсоёмких запросов в СУБД торговой сети».

## Возможности

- подключение PostgreSQL-источников и проверка доступности;
- сбор до 500 наиболее затратных запросов из `pg_stat_statements`;
- поиск, фильтрация, сортировка, пагинация и CSV-экспорт;
- нормализация SQL и SHA-256 fingerprint для поиска версий одного шаблона;
- оценка токсичности по шести ресурсным факторам;
- индекс экологичности, график динамики и практические рекомендации;
- оценка энергии и стоимости по настраиваемым коэффициентам;
- роли владельца, дата-стюарда, администратора и аудитора;
- хеширование паролей `scrypt`, CSRF-защита и шифрование реквизитов источников Fernet;
- журнал действий, подтверждение опасных операций и информативные страницы ошибок;
- retention-политики, архивирование и безопасное удаление;
- полные и инкрементальные JSON-копии с SHA-256, проверкой и восстановлением данных;
- Redis для кэша, блокировки сборщика и ограничения попыток входа с безопасным memory fallback;
- адаптивный веб-интерфейс без мобильного приложения.

## Стек

Python 3.11+, FastAPI, SQLAlchemy 2, PostgreSQL 16, Redis 7, Jinja2 и vanilla JavaScript/CSS. Для автономных тестов используется SQLite.

## Быстрый запуск через Docker Compose

1. Скопируйте настройки:

   ```bash
   cp .env.example .env
   ```

2. Для реального использования замените `SECRET_KEY`, `ENCRYPTION_KEY` и демонстрационные пароли в `.env`.

3. Запустите систему:

   ```bash
   docker compose up --build
   ```

4. Откройте [http://localhost:8000](http://localhost:8000). Документация JSON API доступна на [http://localhost:8000/api/docs](http://localhost:8000/api/docs).

Контейнер PostgreSQL автоматически включает `pg_stat_statements` и `track_io_timing`. Данные PostgreSQL, Redis и резервные копии сохраняются в именованных томах.

## Локальный запуск без Docker

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
cp .env.example .env
DATABASE_URL=sqlite:///./queryguard.db REDIS_URL=redis://127.0.0.1:6379/0 uvicorn app.main:app --reload
```

Если Redis недоступен, приложение продолжит работу с in-memory кэшем. SQLite подходит для демонстрации и тестов; сбор статистики из внешнего источника всё равно рассчитан на PostgreSQL.

## Демонстрационные аккаунты

При `SEED_DEMO=true` создаются пользователи и семь дней обоснованно смоделированной статистики торговой сети.

| Роль | Логин | Пароль | Основные права |
|---|---|---|---|
| Администратор | `admin` | `Admin123!` | пользователи, удаление, retention, backup/restore |
| Дата-стюард | `steward` | `Steward123!` | источники, сбор, каталогизация, архивирование |
| Аудитор | `auditor` | `Auditor123!` | аудит, проверка копий, экспорт без изменения данных |
| Владелец | `owner` | `Owner123!` | свои источники, запросы и показатели |

Отключите `SEED_DEMO` и смените ключи перед публикацией. В production запуск с ключами по умолчанию блокируется.

## Подключение реального PostgreSQL

В целевой СУБД от имени привилегированного пользователя выполните:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
GRANT pg_read_all_stats TO queryguard_monitor;
```

В конфигурации сервера должны быть заданы параметры:

```conf
shared_preload_libraries = 'pg_stat_statements'
track_io_timing = on
pg_stat_statements.track = all
```

После изменения `shared_preload_libraries` PostgreSQL необходимо перезапустить. Для мониторинга рекомендуется отдельный пользователь без прав изменения прикладных таблиц.

## Методика оценки

Каждый фактор нормируется в диапазон от 0 до 1. Итоговая токсичность запроса:

```text
T = 100 × (0.25 × latency
         + 0.20 × total_time
         + 0.20 × io
         + 0.15 × temp_spill
         + 0.10 × cache_miss
         + 0.10 × wal)
```

Пороговые значения нормализации заданы в `app/analytics.py`: 5 секунд среднего времени, 10 минут суммарного времени, 2 ГБ I/O, 512 МБ временных блоков и 1 ГБ WAL. Индекс экологичности равен `100 − T`, а сводное значение взвешивается по суммарному времени выполнения. Значения и веса должны быть обоснованы в пояснительной записке и при необходимости откалиброваны на фактической нагрузке.

Энергия оценивается как сумма CPU-компоненты и I/O-компоненты. Удельная мощность CPU, кВт·ч на ГБ I/O и тариф задаются администратором на странице «Жизненный цикл».

## Архитектура

```text
Браузер / Jinja2 UI
        │
        ▼
FastAPI ── роли, CSRF, REST/HTML, аудит
   │                │
   ▼                ▼
SQLAlchemy      Redis / memory fallback
   │            кэш, rate limit, lock
   ├── служебная БД QueryGuard
   └── PostgreSQL-источник → pg_stat_statements
```

- `app/main.py` — маршруты, авторизация и веб-интерфейс;
- `app/models.py` — ORM-модели;
- `app/services.py` — сбор, демо-данные, retention и копии;
- `app/analytics.py` — нормализация SQL, токсичность, энергия и дашборд;
- `app/security.py` — пароли, шифрование и CSRF;
- `app/cache.py` — Redis и резервный memory backend;
- `app/templates` и `app/static` — серверный UI;
- `tests` — автоматические проверки ключевых сценариев.

## Резервное копирование

Полная копия сохраняет пользователей, источники, снимки запросов, аудит, retention-политики и настройки. Инкрементальная копия содержит записи, созданные или изменённые после последней проверенной копии и ссылку на родителя. Перед восстановлением повторно проверяются SHA-256, формат и вся цепочка до полной копии. Восстановление выполняет контролируемый upsert данных и само фиксируется в журнале аудита.

## Тесты


Проверяются формула токсичности, fingerprint SQL, криптография паролей и реквизитов, авторизация и роли, изоляция данных владельца, dashboard/API и цикл backup → verify → restore.
